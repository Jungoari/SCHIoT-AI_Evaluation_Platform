## 1. 평가자는 누구이고, 어떻게 볼까 (역지사지)

**평가자 = 학과장/교수진.** 이 시스템을 **실제로 다음 학기 수업에 쓸 사람**이다 (1등 팀에 추가 개발 요청 → 실사용 의도가 분명함).

평가자의 예상 행동 순서와 우리의 대응:

| 순서 | 평가자 행동 | 평가자 머릿속 질문 | 우리가 준비할 것 |
|---|---|---|---|
| 1 | GitHub 링크 클릭 (첫 30초) | "뭘 만든 거지? 완성도는?" | README 최상단: 한 줄 소개 + **대표 GIF** + 핵심 기능 배지 |
| 2 | README 스크롤 | "우리가 요구한 거 다 했나?" (40점) | **RFP 요구사항 추적표**: 요구사항 → 구현 위치 → GIF/스크린샷 링크 |
| 3 | 발표 자료 열람 | "왜 이렇게 설계했지? 고민의 깊이는?" | 문제→명분→해결 구조의 스토리, 아키텍처 그림 |
| 4 | (선택) 직접 실행 | "설치 귀찮으면 안 돌려볼 것" | **명령 1줄 실행** + 역할별 데모 계정 + 미리 채워진 데모 대회 |
| 5 | 비교 평가 | "다른 팀보다 뭐가 나은가?" (20점) | 부정 탐지·재현 검증·관리자 업무 자동화 수치 ("검토 시간 N분→M분") |

**결론:** 기능을 만드는 만큼 **"평가자가 확인하기 쉬운 증거"를 만드는 것**이 중요하다. 그래서 GIF 제작을 스크립트로 자동화(10.4절)하고, 추적표를 1급 산출물로 취급한다.

## 2. Kaggle은 왜 성공했나 → 우리가 가져올 것

Kaggle 같은 경진 플랫폼의 장점과, 그것을 **수업 환경**에 맞게 바꿔야 하는 이유.

| # | Kaggle의 장점 | 왜 효과가 있나 | 우리 적용 | 수업 환경이라 바꾼 점 |
|---|---|---|---|---|
| K1 | **즉시 자동 채점** | 제출 직후 점수를 보니 "고치고 다시 내기" 학습 루프가 빨라짐 | CSV 업로드 즉시 채점 | 동일 |
| K2 | **실시간 리더보드** | 경쟁·동기 부여, 내 위치를 객관적으로 앎 | 프로젝트별 리더보드 | 학생끼리는 **익명**, 관리자만 실명 (성적은 개인정보) |
| K3 | **제출 횟수 제한** | 테스트셋 점수를 보면서 찍어 맞추기(프로빙)·과적합 방지 | 마감일별 횟수 제한 | 시스템/형식 오류는 **차감 안 함** (학생 보호) |
| K4 | **Sample Submission 제공** | 형식 오류를 줄여 참가자 좌절 감소 | 샘플 CSV·템플릿 노트북 다운로드 + **업로드 전 사전 검사** | 오류 메시지를 "몇 행, 무엇이 잘못" 수준으로 구체화 |
| K5 | **정답 비공개** | 공정성의 근본 | 레이블은 채점 서버만 접근 | 참여자 코드 실행 시에도 격리 |
| K6 | **상위권 코드 검증** (수상자는 코드 제출·재현) | 리더보드 점수 ≠ 실력인 경우 걸러냄 | 관리자1 검토 → 관리자2 승인 | 상위부터 순차 검토, 부적합이면 **다음 기록**으로 자동 이동 |
| K7 | **Code Competition** (Kaggle 환경에서 노트북 실행) | 손으로 만든 CSV 원천 차단 | **샌드박스 재실행으로 CSV 재현 검증** | 비용 때문에 전원이 아닌 **검토 대상만** 실행 |
| K8 | **Public / Private 리더보드 분리** | 공개 점수에만 과적합하는 것 방지 | *(선택 기능)* 토글로 제공 | 기본값 OFF — RFP는 단일 점수 기준 |
| K9 | **제출 이력·점수 추이** | 자기 성장 확인 | 내 제출 히스토리 + 점수 추이 차트 | 동일 |

> **발표에서 쓸 문장:** "우리는 Kaggle을 베끼지 않았다. Kaggle이 *공개 대회*에서 해결한 문제(공정성·동기·재현성)를 *수업 평가*라는 맥락(성적·개인정보·조교 업무량)에 맞게 다시 설계했다."

## 4. 역할별 UX 설계

### 4.1 설계 원칙
1. **역할마다 첫 화면이 "지금 할 일"**: 참여자는 마감 D-day와 남은 횟수, 관리자1은 검토 대기 건수, 관리자2는 승인 대기 건수
2. **상태를 색으로 일관되게**: 대기(회색)·검토 중(파랑)·통과(초록)·부적합(빨강)·채점 제외(주황) — 모든 화면 공통
3. **실패해도 안심**: 오류 시 "횟수 차감 없음"을 명시적으로 표시
4. **한 화면에서 판단 완료**: 검토자가 탭을 오가지 않게 근거를 한곳에 모음

### 5.4 핵심 로직별 구현 전략

#### ① 마감 규칙 (F-21, F-22)
1. `POST /submit/start` → 서버가 `started_at = now()` 기록, 파일별 SHA-256 선언값 저장, 티켓 발급
2. 업로드 완료 시 해시 대조 → 불일치면 거부
3. 판정:
   - `started_at ≤ 마감` 이고 `completed_at ≤ started_at + 유예시간` → **채점**
   - `started_at > 마지막 마감` → **접수만, 채점 제외**
4. 소속 마감 구간 = `started_at` 이후 가장 가까운 마감일

#### ② 횟수 차감 (F-31, F-32) — 슬롯 예약
```
시작 시: 트랜잭션 + 행 잠금으로 (확정 사용 + 진행 중 예약) < 한도 확인 → 예약
채점 성공      → 예약을 '사용'으로 확정 (−1)
형식/시스템 오류 → 예약 해제 (차감 없음)
부적합 판정     → 이미 '사용'이므로 그대로 유지
```
시스템 오류는 자동으로 재시도(최대 3회)하고, 그래도 실패하면 "차감 없음" 안내를 표시한다.

#### ③ CSV 검증 (F-13, F-33)
검사 순서 (첫 실패에서 멈추지 않고 **오류를 모아서** 최대 20개까지 보고):
인코딩(UTF-8/BOM) → 헤더 일치 → 행 수 → ID 집합 일치(누락·중복·여분) → 값 타입/허용 레이블/범위 → 결측치.
pandas `dtype=str`로 읽어 자동 형 변환에 의한 오판을 막고, 파일 크기 상한도 둔다.

#### ④ 채점 (F-12, F-15)
지표를 레지스트리(플러그인) 형태로 구현: `accuracy, macro_f1, rmse, mae, roc_auc, log_loss` 등.
각 지표는 `higher_is_better` 기본값을 가지며 관리자가 덮어쓸 수 있다. 저장은 원값, 비교·동점 판정은 설정된 자릿수로 반올림한 값.

#### ⑤ 리더보드 (F-40~43)
- 참여자별 대표 점수 = 채점된(GRADED) 제출 중 부적합(REJECTED)이 아닌 것의 최고점
- 순위 = 표준 경쟁 순위(1, 1, 3)
- 렌더링: 요청자의 역할에 따라 실명/별칭 선택 → **서버에서 결정** (실명을 HTML에 숨겨 보내는 방식 금지)
- HTMX로 30초 주기 자동 갱신

#### ⑥ 검토 상태 머신 (F-44, F-45)
```
                ┌──────────── 관리자2 부적합 승인 ────────────┐
                ▼                                              │
[다음 후보 선정] → PENDING → (관리자1 제안) → PROPOSED → (관리자2) ┤
 최고점, 동점이면 최신                                          └→ APPROVED = 대표 기록·성적 확정
```
- 후보 선정 함수는 순수 함수로 만들어 단위 테스트를 철저히 한다 (가장 틀리기 쉬운 로직)
- 관리자1이 부적합으로 제안해도 리더보드 순위는 유지되고, 배지만 "검토 중"으로 표시
- 모든 전이는 감사 로그에 기록

## 6. 부정 제출 탐지 (무결성 리포트) — RFP p.8 ★ 대응

RFP 예시: **① 다른 참여자의 CSV 제출 ② CSV를 직접 기입하거나 생성**

| 검사 | 잡아내는 것 | 방법 | 비용 |
|---|---|---|---|
| I-1 완전 중복 | 타인 CSV 그대로 제출 | 예측값 열 해시 비교 (먼저 제출한 사람 표시) | 매우 낮음 |
| I-2 **오답 일치율** | 타인 CSV를 조금 수정해서 제출 | 두 참여자가 **함께 틀린 문항**에서 같은 오답을 낸 비율. 실력이 비슷하면 정답은 겹치는 게 당연하지만, *오답까지* 똑같은 건 베꼈다는 강한 신호 (시험 부정행위 탐지와 같은 원리) | 낮음 |
| I-3 노트북 정적 분석 | 손으로 만든 CSV | AST로 `fit`/`predict`/`to_csv` 호출 여부, 하드코딩된 긴 리스트, 테스트 특성 파일 로드 여부 확인 | 낮음 |
| I-4 노트북 출력 대조 | 노트북과 CSV 불일치 | 노트북에 저장된 출력 로그(학습 지표)가 있는지, 마지막 실행 순서가 정상인지 | 낮음 |
| I-5 가중치 파일 검증 | 가짜 가중치 | 샌드박스 안에서 로드 가능 여부, 프레임워크·파라미터 수 | 중간 |
| I-6 **추론 재실행** | 위의 모든 경우의 최종 확인 | 샌드박스에서 노트북의 추론 부분을 가중치로 실행 → 생성된 CSV와 제출 CSV의 일치율 | 높음 → **검토 대상만, 버튼으로 실행** |
| I-7 점수 이상치 | 갑작스러운 비정상 점프 | 직전 제출 대비 급격한 향상 + 코드 변화가 거의 없음 | 낮음 |

**검증 시간 단축 전략 (I-6):** 학습부터 다시 돌리면 오래 걸리므로, **템플릿 노트북에 `inference` 태그 셀**을 두도록 안내하고 그 셀만 가중치로 실행한다 (papermill/nbclient로 태그 셀만 실행). 템플릿을 따르지 않은 노트북은 전체 실행으로 대체(시간 제한 적용).

**리포트 표시:** 🟢 이상 없음 / 🟡 확인 권장 / 🔴 강한 의심 + 근거 한 줄씩. **자동으로 부적합 처리하지는 않는다** — 최종 판단은 사람(관리자1→관리자2)이 한다는 RFP 원칙을 지키고, 시스템은 "어디를 볼지" 알려 주는 역할만 한다.

### 10.4 GIF 제작 계획
**방식:** Playwright 시나리오 스크립트로 화면 녹화 → ffmpeg + gifski로 변환.
**명분:** UI를 고칠 때마다 손으로 다시 녹화하지 않고 **명령 한 번으로 전체 GIF를 재생성** → 마지막 날 디자인을 수정해도 GIF가 항상 최신 상태로 유지된다. 이 방식 자체도 발표 소재가 된다.

**규격:** 1280×720 녹화 → 960px 폭 GIF, 15fps, 10~20초, 장당 5MB 이하, 마우스 커서와 클릭 하이라이트 표시, 상단에 캡션 바("① 참여 코드로 가입").

| # | GIF | 보여줄 것 | RFP |
|---|---|---|---|
| G1 | 대회 개설 마법사 | 정답 업로드 → 규격 자동 추론 → 참여 코드 발급 | p.3, p.5 |
| G2 | 코드 가입 / 대회 추가 | 신규 가입 + 기존 회원 코드 추가 | p.3 |
| G3 | **제출 & 즉시 채점** (대표) | 드래그 → 사전 검사 → 진행률 → 점수·순위 | p.4~5 |
| G4 | 형식 오류 | 구체적 오류 메시지 + "차감 없음" | p.5 |
| G5 | 마감 경계 | 마감 직전 시작 → 마감 후 완료 → 채점됨 / 마감 후 제출 → 채점 제외 | p.4 |
| G6 | 리더보드 익명 vs 실명 | 같은 리더보드를 참여자·관리자 화면으로 나란히 비교 | p.6 |

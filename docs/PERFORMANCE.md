# 성능 · 자원 사용량 측정

> 평가 기준 "시스템 설계 및 보안 고려 — 유지보수, **자원 사용량**" 대응 자료
> 측정일 2026-11-19 · 측정 환경: Apple M2 노트북, Docker Desktop (CPU 8개·메모리 7.75GiB 할당), `docker compose` 전체 스택 (gunicorn 워커 3 · 채점 워커 1 · 검증 워커 1)

## 1. 부하 테스트 — "마감 직전 50명이 동시에 제출"

```bash
python manage.py loadtest_users --count 50          # 웹 컨테이너 안에서 (DEMO_MODE 전용)
python scripts/loadtest.py http://localhost:8000 50
```

50개 스레드가 동시에 업로드 티켓 발급 → 3종 파일 업로드(가중치 약 2MB) → 채점 완료까지 상태를 폴링한다.

| 지표 | 중앙값 | p95 | 최대 |
|---|---:|---:|---:|
| 업로드 티켓 발급 | 0.10초 | 0.18초 | 0.19초 |
| 파일 업로드 (약 2MB) | 0.54초 | 0.79초 | 0.81초 |
| 업로드 완료 → 채점 완료 | 2.19초 | 3.47초 | 3.73초 |
| **시작 → 채점 완료** | **2.85초** | **4.44초** | **4.72초** |

**50건 전부 성공, 실패 0건, 전체 소요 4.7초.** 채점 워커 1개가 594행 CSV 50건을 직렬로 처리해도 학생 입장 대기 시간은 5초 이내다.
채점은 큐로 분리되어 있어 웹 응답(티켓 발급 0.1초)은 부하와 무관하게 유지된다.

## 2. 자원 사용량

| 컨테이너 | 유휴 메모리 | 부하 중 최대 메모리 | 부하 중 최대 CPU |
|---|---:|---:|---:|
| web (gunicorn 3) | 258 MiB | 482 MiB | 243% (CPU 2.4개) |
| worker (채점) | 151 MiB | 156 MiB | 87% |
| sandbox-worker | 151 MiB | 151 MiB | 0.5% |
| db (PostgreSQL) | 30 MiB | 41 MiB | 32% |
| redis | 10 MiB | 12 MiB | 3% |
| **합계** | **약 600 MiB** | **약 840 MiB** | |

→ **학과 단위(학생 수십~수백 명) 운영은 노트북 1대 또는 2GB 메모리 소형 VM으로 충분**하다.

### 샌드박스 재실행 (I-6)

| 항목 | 값 |
|---|---|
| 실행 1건 소요 | 약 2.5~3초 (inference 태그 셀만 실행, 학습 재실행 없음) |
| 컨테이너 제한 | 메모리 2GB · CPU 1개 · 프로세스 128개 · 300초 · 네트워크 없음 |
| 실행 대상 | 검토 대상 기록만, 관리자가 버튼으로 요청 (전체 자동 실행 안 함 → 자원 절약) |
| 이미지 크기 | 약 960MB (pandas·scikit-learn·nbclient) |

### 자원 절약 설계

| 결정 | 효과 |
|---|---|
| 채점은 CSV 파싱만 (코드 실행 없음) | 제출 1건 채점이 수십 ms 수준 |
| 재실행은 검토 대상만 + inference 셀만 | 전원 노트북 재실행 대비 컴퓨팅 비용 대폭 절감 |
| 무결성 비교는 참여자별 최근 5건으로 제한 | 제출이 늘어도 비교 비용 상한 고정 |
| 업로드는 청크 스트리밍 저장 (5MB 초과 시 임시 파일) | 500MB 가중치도 메모리를 거의 쓰지 않음 |
| 리더보드는 30초 간격 HTMX 부분 갱신 | 페이지 전체 새로고침 대비 트래픽 감소 |

## 2-1. 화면별 DB 쿼리 수 — "학생이 늘어도 화면이 느려지지 않는가"

데모 데이터(참여자 14명)에서 화면마다 실행되는 DB 쿼리를 세고, **같은 쿼리가 참여자 수만큼 반복되는 곳(N+1)** 을 찾았다

| 화면 | 쿼리 수 | 비고 |
|---|---:|---|
| 최종 성적 (관리자) | 23 → **11** | 참여자마다 검토 기록을 따로 조회 → 한 번에 조회로 수정. 50명이면 59 → 11 |
| 검토 큐 · 리더보드 · 설정 · 회원 · 감사 로그 | 5~11 | 참여자 수와 무관 |
| 관리자 대시보드 | 35 | 프로젝트 수에 비례 (대회당 2~5개라 허용), 참여자 수와 무관 |
| 참여자 대시보드 · 대회 홈 · 프로젝트 | 11~24 | 프로젝트 수에 비례, 참여자 수와 무관 |

회귀 테스트 `apps/review/tests/test_query_counts.py`: 참여자 3명 → 9명으로 늘려도 최종 성적·검토 큐·리더보드의 쿼리 수가 **같아야** 통과 (수정 전 코드로 돌리면 13 → 19 로 실패하는 것을 확인)

## 3. 업무 시간 비교 (추정)

> 아래 '수작업' 시간은 우리가 가정한 추정치다. 실제 조교 업무 시간은 사용성 테스트에서 측정해 보완한다.

| 업무 (학생 50명 · 제출 150건 기준) | 수작업 (추정) | 시스템 |
|---|---:|---:|
| 채점·점수 기록 (건당 1분) | 약 150분 | 0분 (자동, 50건 동시 4.7초) |
| 형식 오류 안내·재제출 요청 (오류 20건 × 3분) | 약 60분 | 0분 (업로드 전 자동 안내, 횟수 미차감) |
| 순위표 작성·공지 | 약 20분 | 0분 (실시간 리더보드) |
| 부정 의심 1차 선별 (노트북 50개 × 3분) | 약 150분 | 신호등 확인 → 🔴🟡만 정밀 검토 |
| 성적표 정리 | 약 20분 | CSV 내보내기 1클릭 |

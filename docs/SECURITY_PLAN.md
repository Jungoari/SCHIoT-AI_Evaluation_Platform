## 2. 누가 공격하나 (위협 모델)

| 공격자 | 동기 | 대표 공격 |
|---|---|---|
| **점수를 올리고 싶은 참여자** (가장 현실적) | 성적 | 노트북 실행 시 정답 파일 읽기, 리더보드 프로빙, 타인 CSV 복사, 마감 후 파일 바꿔치기, 동시 제출로 횟수 초과 |
| 호기심 많은 참여자 | 재미·과시 | 노트북에 XSS를 심어 관리자 세션 탈취, URL을 바꿔 남의 제출물 열람(IDOR) |
| 외부인 | 무작위 공격 | 무차별 로그인 대입, 알려진 취약점 스캔, 대용량 업로드로 서버 마비 |
| 내부자 (관리자1) | 실수 또는 편파 | 권한 밖 대회 접근, 판정 기록 은폐 |

**설계 원칙**
- **최소 권한** — 각 구성 요소는 꼭 필요한 데이터만 접근
- **심층 방어** — 하나가 뚫려도 다음 방어선이 있음
- **기본 거부** — 명시적으로 허용하지 않은 것은 모두 거부
- **사람의 최종 판단** — 자동 판정은 제안까지만

## 3. RFP 보안 요구사항별 대응

### 3.1 참여자 코드 실행 격리 (정답·비밀키·타인 자료·관리 인터페이스 차단)

**구조적 분리 (가장 중요):**
```
[채점 워커]   정답 O · 참여자 코드 실행 X   ← CSV는 "데이터"로만 파싱
[검증 워커]   정답 X · 샌드박스 실행만 지시
   └ [샌드박스 컨테이너] 정답 X · 비밀키 X · 네트워크 X · 해당 제출 파일만 존재
```
참여자 코드가 실행되는 공간에는 **훔칠 정답이 처음부터 존재하지 않는다.**

**샌드박스 컨테이너 설정:**
| 설정 | 막는 것 |
|---|---|
| `--network none` | 외부로 정답 전송, 내부 관리 API·DB·Redis 접근 |
| `--read-only` + `tmpfs /work` (크기 제한) | 시스템 파일 변조 |
| `--user 65534` (비루트), `--cap-drop ALL`, `no-new-privileges` | 권한 상승 |
| `--memory`, `--cpus`, `--pids-limit`, 실행 시간 제한 | 무한 루프, 포크 폭탄, 메모리 고갈 |
| 환경 변수 비움, 호스트 볼륨은 해당 제출물만 **읽기 전용** 마운트 | 비밀키 노출, 다른 참여자 파일 접근 |
| Docker 소켓 미마운트, 기본 seccomp 프로파일 유지 | 컨테이너 탈출 |
| 실행할 때마다 새 컨테이너 생성 → 종료 후 삭제 | 이전 실행 흔적 엿보기 |

**가중치 파일(pickle) 위험:** `.pkl`, `.joblib`, `.pt`는 내부적으로 pickle 형식이라 **불러오는 순간 임의 코드가 실행될 수 있다.** → 웹 서버나 채점 워커에서는 절대 로드하지 않고, **샌드박스 안에서만** 로드한다. PyTorch는 `weights_only=True`를 사용하고, `safetensors`/ONNX 형식을 권장 형식으로 안내한다.

### 3.2 파일 내용 검증과 안전한 저장명

| 파일 | 확장자 외 내용 검증 |
|---|---|
| `.csv` | UTF-8 디코딩 성공, CSV 파서로 파싱 성공, 행·열 상한, 바이너리 바이트(NUL) 없음 |
| `.ipynb` | JSON 파싱 + `nbformat.validate` 스키마 검증, 크기 상한 |
| 가중치 | 허용 확장자 목록 + 매직 바이트 확인 (zip: `.pt`·`.keras`, HDF5 시그니처: `.h5`, pickle 프로토콜 헤더: `.pkl`), 크기 상한 |

- 저장 파일명 = **UUID** (원본 이름은 DB에만 저장, 화면 표시 시 이스케이프) → 경로 조작(`../../`)과 덮어쓰기 차단
- 저장 위치는 **웹 루트 밖** → URL로 직접 접근 불가
- 다운로드는 권한 검사를 거치는 뷰를 통해서만, `Content-Disposition: attachment` + `X-Content-Type-Options: nosniff`
- 업로드 크기 상한은 Nginx와 Django 양쪽에 설정

### 3.3 노트북의 비신뢰 HTML·스크립트·위젯 처리

노트북의 출력 칸에는 `text/html`, `application/javascript`, 위젯 상태가 들어갈 수 있다 → 관리자가 열람하는 순간 실행되는 **저장형 XSS** 위험.

1. **서버에서 정제**: 렌더링 전에 `application/javascript`, 위젯 출력, `<script>`·이벤트 핸들러·`javascript:` URL 제거. HTML 출력은 nh3(허용 목록 기반 sanitizer)로 정제하고, 마크다운 셀도 동일하게 처리
2. **격리 표시**: 정제된 결과를 `sandbox` 속성(스크립트 허용 안 함) iframe 안에 표시 → 정제를 우회하더라도 스크립트 실행 불가, 부모 페이지 쿠키 접근 불가
3. **CSP**: 노트북 뷰 응답에 `script-src 'none'` 적용
4. 이미지는 base64 PNG/JPEG만 허용 (SVG는 스크립트를 포함할 수 있어 래스터 변환 후 표시하거나 제외)

### 3.4 비밀번호·세션·비밀 정보 관리, 내부 정보 노출 금지

| 항목 | 조치 |
|---|---|
| 비밀번호 | **Argon2** 해시 (솔트 자동 적용), 최소 길이 + 흔한 비밀번호 차단 (Django 비밀번호 검증기) |
| 로그인 대입 | 계정·IP별 실패 횟수 제한 후 잠금 (django-axes) |
| 세션 | `HttpOnly`, `Secure`, `SameSite=Lax` 쿠키, 로그인 시 세션 ID 재발급, 유휴 시간 만료, 비밀번호 변경 시 다른 세션 무효화 |
| CSRF | Django CSRF 미들웨어 (HTMX 요청에도 토큰 포함) |
| 참여 코드 | 충분한 길이의 난수(`secrets` 모듈)로 생성, DB에는 해시로 저장, 만료·재발급 가능 |
| 비밀 정보 | `SECRET_KEY`·DB 비밀번호는 `.env`에만 저장 (gitignore), 저장소에는 `.env.example`만 포함. 소스 코드 하드코딩 금지 |
| 정답 파일 | 채점 워커만 마운트하는 별도 볼륨에 저장, 웹 컨테이너에는 업로드 경로만 존재 |
| 오류 응답 | `DEBUG=False`, 공통 오류 페이지에 **추적 ID만** 표시 ("문의 시 이 번호를 알려주세요") → 상세 내용은 서버 로그에서 추적 ID로 조회 |
| 로그 | 비밀번호·세션·토큰·정답 값은 기록하지 않음 (로깅 필터로 마스킹) |
| 참여자 응답 | 다른 참여자 존재 여부, 정답 분포, 서버 경로가 드러나지 않게 함. CSV 오류 메시지에도 "정답 값"은 포함하지 않음 |
| 보안 헤더 | HSTS, CSP, `X-Frame-Options`, `Referrer-Policy` |

### 3.5 관리자 권한·승인 절차 분리와 중요 변경 기록

**권한 분리:**
- 모든 권한 판단을 **한 모듈(`permissions.py`)의 정책 함수**로 모아 둠 → 뷰마다 제각각 구현하다 빠뜨리는 일 방지
- 대회 단위 역할 (`Membership`) → 관리자1은 **자기가 담당한 대회만** 접근
- 객체 단위 확인: URL의 ID를 바꿔 남의 제출물을 여는 공격(IDOR) 차단 — 모든 조회 쿼리에 "요청자 범위" 조건을 적용
- **승인 절차를 코드로 강제**: 상태 머신에서 `PROPOSED → APPROVED/REJECTED` 전이는 관리자2만 가능, 관리자1의 제안은 순위에 영향 없음
- 관리자2가 자기가 직접 제안한 건을 승인하는 경우 화면에 표시 (자기 승인 경고)

**감사 로그 대상:**
대회·프로젝트·마감·횟수·지표·규격 변경 / 정답 업로드·교체 / 재채점 / 판정 제안·승인 / 역할 변경·코드 발급 / 성적 확정·내보내기 / 실명 정보 열람(선택) / 로그인 실패·잠금

**위변조 방지:** 각 로그에 `hash = SHA256(이전 hash + 내용)`를 저장하는 해시 체인 → 중간 기록을 삭제하거나 수정하면 검증 명령에서 체인이 끊긴 것으로 드러남. 애플리케이션에서는 로그의 수정·삭제 기능 자체를 제공하지 않음.

## 4. 행정안전부 「소프트웨어 개발보안 가이드」 대응표

가이드의 **구현단계 보안약점(7개 분류)** 중 본 시스템과 관련된 항목을 대응시킨다. 실제 작성 시 최신판 가이드 원문과 항목명을 다시 대조해 확정한다.

| 분류 | 보안약점 | 이 시스템에서의 위험 지점 | 대응 |
|---|---|---|---|
| 입력데이터 검증 및 표현 | SQL 삽입 | 검색·필터 | Django ORM만 사용, 원시 SQL 금지 |
| | 경로 조작 및 자원 삽입 | 업로드 파일명 | UUID 저장명, 경로 정규화 검사 |
| | 크로스사이트 스크립트(XSS) | 노트북, 코멘트, 대회 설명 | 템플릿 자동 이스케이프, nh3 정제, 격리 iframe, CSP |
| | 운영체제 명령어 삽입 | 샌드박스 실행 | 셸을 거치지 않고 Docker SDK에 인자 배열로 전달 |
| | 위험한 형식 파일 업로드 | 3종 제출 파일 | 3.2절 내용 검증, 웹 루트 밖 저장 |
| | 크로스사이트 요청 위조(CSRF) | 판정·승인·설정 변경 | CSRF 토큰, 상태 변경은 POST만 허용 |
| | 서버사이드 요청 위조(SSRF) | (외부 URL 입력 기능 없음) | 외부 URL을 서버가 가져오는 기능을 만들지 않음 |
| | 보안기능 결정에 사용되는 부적절한 입력값 | 역할·사용자 ID를 폼 값으로 받는 경우 | 역할·소유자는 항상 서버 세션 기준으로 판단 |
| 보안기능 | 적절한 인증 없는 중요 기능 허용 / 부적절한 인가 | 관리자 기능, 타인 제출물 | 정책 모듈 + 권한 매트릭스 테스트 |
| | 중요한 자원에 대한 잘못된 권한 설정 | 업로드·정답 디렉터리 | 컨테이너별 볼륨 분리, 파일 권한 600 |
| | 하드코드된 중요정보 | 설정 파일 | `.env` 분리, `bandit`으로 검사 |
| | 적절하지 않은 난수 값 사용 | 참여 코드, 익명 별칭 | `secrets` 모듈 사용 (`random` 금지) |
| | 취약한 비밀번호 허용 / 솔트 없는 해시 | 회원가입 | 비밀번호 검증기, Argon2 |
| | 반복된 인증 시도 제한 기능 부재 | 로그인, 코드 입력 | 실패 횟수 제한 (코드 입력에도 적용 → 코드 무차별 대입 방지) |
| | 주석문 안에 포함된 시스템 주요정보 | 템플릿 | 배포 전 검토, HTML 주석 금지 규칙 |
| 시간 및 상태 | 경쟁조건(TOCTOU) | **제출 횟수 확인 후 차감** | 트랜잭션 + 행 잠금 + 슬롯 예약 |
| | 종료되지 않는 반복문·재귀 | 참여자 노트북 | 샌드박스 실행 시간·자원 제한 |
| 에러처리 | 오류 메시지 정보노출 | 500 오류, CSV 오류 메시지 | 추적 ID 방식, 정답 값 미포함 |
| | 오류상황 대응 부재 / 부적절한 예외 처리 | 채점 실패 | SYSTEM_ERROR 상태, 횟수 미차감, 재시도 |
| 코드오류 | **신뢰할 수 없는 데이터의 역직렬화** | **가중치 pickle 파일** | 샌드박스 내부에서만 로드, `weights_only=True` |
| | 부적절한 자원 해제 | 임시 파일, 컨테이너 | `with` 문 사용, 종료 후 컨테이너 자동 삭제 |
| 캡슐화 | 잘못된 세션에 의한 데이터 정보노출 | 리더보드 실명 | 서버에서 역할별로 렌더링, 응답에 실명 미포함 |
| | 제거되지 않고 남은 디버그 코드 | 배포 설정 | `DEBUG=False`, 배포 점검표 |
| API 오용 | 취약한 API 사용 | `pickle`, `eval`, `subprocess(shell=True)` | 사용 금지, `bandit`으로 검사 |

## 5. 리더보드 관련 공정성 보안

| 공격 | 대응 |
|---|---|
| 프로빙 (점수 변화로 정답 역추적) | 제출 횟수 제한, (선택) Public/Private 분리 |
| 다중 계정으로 횟수 우회 | 코드 가입 + 실명 확인은 관리자 화면에서, 무결성 검사 I-2(오답 일치율)로 계정 간 동일 제출 탐지 |
| 마감 후 파일 바꿔치기 | 시작 시 해시 선언, 유예 시간 제한 |
| 타인 CSV 복사 | 무결성 검사 I-1, I-2 |
| 손으로 만든 CSV | I-3 정적 분석, I-6 재실행 검증 |

## 6. 가용성 (서비스 장애·자원 공격)

- 요청 크기 상한, 로그인·제출 API 속도 제한 (rate limit)
- 채점·샌드박스는 큐로 분리 + 동시 실행 수 제한 → 마감 직전 폭주에도 웹은 응답 유지
- 사용자별 진행 중 업로드 개수 제한

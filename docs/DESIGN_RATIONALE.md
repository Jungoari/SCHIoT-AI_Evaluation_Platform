# 핵심 요구사항 구현 방법과 명분

> RFP 요구사항 중 **점수와 신뢰에 직결되는 9가지**를 "무엇을 요구하나 → 왜 중요한가 → 어떻게 만드나 → 왜 이 방법인가" 순서로 정리했다.
> 발표 자료 좌측 패널(요구사항 / 중요한 이유 / 해결 방법)의 원본으로 사용한다.

비유 하나로 시작하면 이해가 쉽다. **이 시스템은 "온라인 시험장"이다.**
참여자는 수험생, 관리자1은 감독관, 관리자2는 시험위원장, 정답 CSV는 답안지 원본이다.

---

## 1. 정답 보호 — "답안지 원본은 금고에"

| | |
|---|---|
| **RFP 요구** | 참여자에게 레이블 비노출, 관리자·채점 시스템만 접근 (p.2, p.5). 참여자 코드 실행 시 정답·비밀키·타인 자료·관리 기능 접근 차단 (p.7) |
| **왜 중요한가** | 정답이 한 번 새면 대회 전체가 무효가 된다. 되돌릴 방법이 없는 유일한 사고 |
| **어떻게** | 서버를 역할별로 쪼갠다. **채점 워커**는 정답을 보지만 참여자 코드를 실행하지 않고, **샌드박스**는 참여자 코드를 실행하지만 정답이 없다. 샌드박스는 인터넷 차단·읽기 전용·자원 제한 상태로 실행 |
| **왜 이 방법인가** | "코드가 정답을 못 읽게 막는" 방식은 막는 규칙 하나만 빠져도 뚫린다. **정답이 아예 없는 방에서 실행**하면 실수가 있어도 훔칠 것이 없다. 보안 용어로 *최소 권한*·*심층 방어* |

---

## 2. 마감 규칙 — "시험 종료 전에 답안을 내기 시작했으면 인정"

| | |
|---|---|
| **RFP 요구** | 마감 전 업로드 시작 → 마감 후 완료돼도 채점. 마감 후 새 제출은 접수만 하고 채점하지 않음 (p.4) |
| **왜 중요한가** | 가중치 파일은 수백 MB일 수 있다. 네트워크 탓으로 0점이 되면 억울하고, 반대로 이 규칙을 악용하면 불공정해진다 |
| **어떻게** | ① 업로드 버튼을 누르는 순간 서버가 **"업로드 티켓"**을 발급하고 시작 시각을 기록 ② 이때 파일의 **지문(SHA-256 해시)**도 함께 등록 ③ 업로드가 끝나면 지문이 일치하는지 확인 ④ 시작 시각이 마감 전이고 유예 시간(기본 30분) 안에 끝났으면 채점 |
| **왜 이 방법인가** | 시각은 **서버 시계**만 믿는다 (브라우저 시계는 조작 가능). 지문을 먼저 받는 이유: 지문이 없으면 "마감 1초 전에 티켓만 받아 두고, 마감 후 더 좋은 파일을 천천히 올리는" 꼼수가 가능하다. 지문은 시험지에 먼저 서명하게 하는 것과 같다 → **RFP가 놓친 허점을 우리가 발견해 막은 사례** |

## 3. 제출 횟수 — "기회는 정해진 만큼, 억울한 차감은 없게"

| | |
|---|---|
| **RFP 요구** | 마감일별 횟수 제한. 정상 채점은 1회 차감, 형식 오류·시스템 오류는 미차감, 부적합 판정은 차감 유지. 사용·남은 횟수 표시 (p.5) |
| **왜 중요한가** | 무제한이면 CSV를 조금씩 바꿔 가며 점수 변화로 정답을 알아낼 수 있다 (리더보드 프로빙). 반대로 서버 오류로 기회를 잃으면 학생이 손해 |
| **어떻게** | **좌석 예약 방식**. 제출을 시작하면 남은 횟수에서 한 칸을 "예약" → 채점 성공 시 "사용"으로 확정, 오류면 예약 취소. 예약할 때 DB에 잠금을 걸어 한 번에 한 요청만 처리 |
| **왜 이 방법인가** | 단순히 "남은 횟수 확인 → 나중에 차감"으로 만들면, 남은 횟수 1회일 때 탭 10개로 동시에 제출하면 10개가 모두 확인을 통과한다 (*경쟁 조건*, 행안부 가이드의 "경쟁조건" 보안약점). 영화관 좌석처럼 **먼저 잡은 사람만** 앉게 하면 해결된다 |

## 4. CSV 형식 검사 — "답안지 양식이 맞는지 먼저 확인"

| | |
|---|---|
| **RFP 요구** | 채점 전 관리자2가 등록한 형식과 비교 (허용 레이블, 행·열 수 등). 형식 오류는 채점 불가, 차감 없음 (p.4~5) |
| **왜 중요한가** | 형식이 틀린 파일이 채점기에 들어가면 에러가 나거나 엉뚱한 점수가 나온다. 학생 입장에서는 "왜 틀렸는지"를 모르는 것이 가장 답답하다 |
| **어떻게** | ① 관리자2가 정답 CSV를 올리면 시스템이 **규격을 자동 추론** (ID 열, 예측 열, 허용 레이블, 행 수) → 관리자는 확인만 ② 학생이 올리면 브라우저에서 먼저 1차 검사 → 서버에서 다시 정밀 검사 ③ 오류를 한 번에 모아 "152행: 'cat'은 허용 레이블이 아님"처럼 구체적으로 표시 |
| **왜 이 방법인가** | 규격을 손으로 입력하면 오타 하나로 전원이 채점에 실패한다 → **자동 추론으로 관리자 실수를 차단**. 브라우저 사전 검사는 큰 가중치 파일을 다 올린 뒤에 CSV 오류를 알게 되는 시간 낭비를 막는다. 서버 검사를 반드시 한 번 더 하는 이유는 브라우저 검사는 우회할 수 있기 때문 |

## 5. 리더보드 — "실시간 경쟁은 보여 주되, 개인정보는 지킨다"

| | |
|---|---|
| **RFP 요구** | 참여자별 최고 점수 1개, 미검증 기록 포함 + 검증 상태 표시, 동점은 공동 순위, 참여자 화면은 익명·관리자 화면은 실명 (p.6) |
| **왜 중요한가** | 순위는 동기 부여의 핵심이다. 하지만 성적은 개인정보이고, 검증 전 점수를 확정된 것처럼 보이면 나중에 순위가 바뀔 때 분쟁이 생긴다 |
| **어떻게** | ① 대회마다 **무작위 익명 별칭** 부여 (내 행은 "나"로 강조) ② 실명/별칭은 **서버에서** 요청자 역할을 보고 결정해 화면을 만든다 ③ 점수는 원래 값으로 저장하되, 순위 비교는 설정된 소수점 자릿수로 반올림해서 한다 ④ 상태 배지: 대기·검토 중·통과·부적합 |
| **왜 이 방법인가** | 실명을 HTML에 넣고 CSS로 숨기면 개발자 도구로 다 보인다 → **보내지 않는 것이 유일하게 안전한 방법**. 별칭을 사용자 번호로 만들면 역추적이 가능하므로 무작위로 생성. 0.91230000001과 0.9123이 다른 점수로 처리되는 부동소수 오차 때문에 반올림 비교가 필요하다 |

## 6. 2단계 검증과 성적 확정 — "감독관은 의견, 결정은 위원장"

| | |
|---|---|
| **RFP 요구** | 최고 점수 기록부터 관리자1 검토(동점이면 최신부터) → 관리자1은 판정 *제안*만, 제안만으로는 순위 제외 안 됨 → 관리자2 승인: 부적합이면 다음 기록, 통과면 대표 기록 확정 (p.6) |
| **왜 중요한가** | 성적이 걸린 결정을 한 사람이 내리면 실수나 편파를 막을 수 없다. 또 학생 1명당 제출이 수십 건이라 전부 검토하면 끝이 없다 |
| **어떻게** | 기록마다 **상태 머신**(정해진 순서로만 바뀌는 상태 흐름)을 둔다: `대기 → 제안됨 → 승인/부적합`. 부적합이 승인되면 시스템이 그 학생의 **다음 후보를 자동으로 검토 큐에 올린다.** 승인·부적합 전환은 코드에서 관리자2만 할 수 있게 막는다 |
| **왜 이 방법인가** | "위에서부터 내려가다 처음 통과한 기록에서 멈추기" → 검토량이 최소가 된다. 버튼을 숨기는 것만으로는 권한을 지킬 수 없으므로 **상태 전환 자체를 서버 코드가 검사**한다. 모든 전환은 감사 로그에 남아 "누가 언제 왜" 판정했는지 추적 가능 |

## 7. 노트북 안전 처리 — "답안지에 숨긴 함정으로부터 감독관 보호"

| | |
|---|---|
| **RFP 요구** | Notebook의 비신뢰 HTML·스크립트·위젯을 안전하게 처리 (p.7) |
| **왜 중요한가** | `.ipynb` 출력 칸에는 JavaScript를 넣을 수 있다. 관리자가 검토하려고 여는 순간 그 코드가 실행되면 **관리자 계정이 탈취**되고, 그 계정으로 성적을 조작할 수 있다 (저장형 XSS) |
| **어떻게** | ① 서버에서 스크립트·위젯·위험한 HTML 태그를 제거 ② 정제된 결과를 **스크립트 실행이 금지된 격리 iframe** 안에 표시 ③ 보안 정책 헤더(CSP)로 스크립트를 한 번 더 차단 |
| **왜 이 방법인가** | 정제 하나만 믿으면 우회 기법이 나올 수 있다. **3겹 방어**로 하나가 뚫려도 다음 겹이 막는다 |

## 8. 파일 검증과 저장 — "이름표가 아니라 내용물을 확인"

| | |
|---|---|
| **RFP 요구** | 확장자뿐 아니라 파일 내용 검증, 저장명은 안전한 식별자로 관리 (p.7) |
| **왜 중요한가** | `virus.exe`를 `a.csv`로 이름만 바꿀 수 있다. 파일명에 `../../`를 넣으면 서버의 다른 위치에 파일을 덮어쓸 수 있다 (경로 조작) |
| **어떻게** | CSV는 실제로 파싱해 보고, 노트북은 JSON 스키마로 검증하고, 가중치는 파일 앞부분의 고유 서명(매직 바이트)을 확인한다. 저장할 때는 **무작위 UUID 이름**으로 웹 접근이 불가능한 폴더에 저장하고, 원래 이름은 DB에만 기록 |
| **왜 이 방법인가** | 사용자가 정한 이름을 그대로 쓰지 않으면 경로 조작 공격 자체가 불가능해진다. 추가로 발견한 위험: **가중치 파일(pickle)은 불러오기만 해도 안에 든 코드가 실행된다** → 웹 서버에서는 절대 열지 않고 샌드박스 안에서만 연다 (행안부 가이드 "신뢰할 수 없는 데이터의 역직렬화") |

## 9. 부정 제출 판별 — "베낀 답안은 고친 곳이 부자연스럽다"

| | |
|---|---|
| **RFP 요구** | 제출한 CSV가 모델의 추론 결과인지, 우회적 수행인지 판단하는 프로세스 (타인 CSV 제출, 직접 기입·생성) — p.8에서 **유일하게 굵게 강조된 항목** |
| **왜 중요한가** | 지금은 조교가 노트북을 하나하나 열어 봐야 한다. 가장 시간이 오래 걸리고, 놓치기 쉽고, 공정성과 직결되는 업무 |
| **어떻게** | **무결성 리포트**로 1차 자동 선별 → 사람이 최종 판단. ① 완전 중복 CSV 탐지 ② **부분 복사 패턴**: 다른 학생과 대부분 같은데, 서로 갈리는 문항에서 내 답이 *다른 누구도 내지 않은 부자연스러운 답*인지 확인 ③ 노트북 코드 분석: 학습·예측·CSV 저장 코드가 있는지, 예측값을 손으로 적은 긴 리스트가 있는지 ④ 검토 대상만 샌드박스에서 **추론 재실행** → 제출 CSV와 일치율 계산. 결과를 🟢🟡🔴 신호등으로 표시 |
| **왜 이 방법인가** | 처음에는 '오답까지 같으면 복사'라는 기준을 썼지만, 탐지 실험에서 10클래스 문제의 정직한 모델들도 같은 숫자를 헷갈려 55%가 오탐되었다. 그래서 **복사본이 원본과 갈리는 곳은 '손으로 무작위로 고친 곳'이라 다른 모델 누구도 내지 않는 답이 된다**는 점을 이용하도록 바꿨고, 탐지율 100%·오탐 5%가 되었다 (docs/INTEGRITY_EXPERIMENT.md). 비교할 학생이 10명 미만이면 이 판단을 믿을 수 없어 🟡까지만 표시한다. 재실행은 비용이 크니 **검토 대상에만** 실행해 자원을 아낀다. 자동으로 부적합 처리하지 않는 이유: 오탐으로 억울한 학생이 생기면 안 되고, RFP의 "사람이 판정" 원칙을 지키기 위해서다 |

## 보너스: 감사 로그 — "모든 판정에는 기록이 남는다"

| | |
|---|---|
| **RFP 요구** | 관리자별 운영 권한과 승인 절차를 분리하고 중요 변경 사항 기록 (p.7) |
| **어떻게** | 설정 변경·정답 교체·재채점·판정·승인·역할 변경을 모두 기록 (누가·언제·무엇을·변경 전후 값). 각 기록에 앞 기록의 지문을 포함시키는 **해시 체인** |
| **왜 이 방법인가** | 성적 분쟁이 생겼을 때 근거가 된다. 해시 체인은 블록체인과 같은 원리로, 중간 기록 하나를 지우거나 고치면 그 뒤 기록이 전부 맞지 않게 되어 조작이 드러난다 |

## 3. 사용성과 업무 효율 (20점)

### 현재 계획의 강점
- 역할별 첫 화면을 "지금 할 일" 중심으로 구성, 업로드 전 사전 검사, 구체적인 오류 메시지, 검토 단축키, 일괄 승인, 규격 자동 추론

### 약점 (−5점 추정)
- "편하다", "시간이 줄어든다"는 **주장만 있고 숫자가 없음**
- 실제 사용자(학생·조교)로 시험해 본 적이 없음

### 보강

| 보강 | 방법 | 결과물 | 소요 |
|---|---|---|---|
| **업무 시간 측정** | 같은 작업을 "수작업 방식"과 "시스템"으로 각각 시간 측정. 예: 30명분 CSV 채점·순위 정리, 대회 1개 개설, 검토 10건 | "조교 업무 N분 → M분 (−X%)" 표, 발표 핵심 슬라이드 | 2시간 |
| **사용성 테스트** | 학과 동기 3~5명에게 과제 3개 수행 요청 (가입→제출, 오류 수정 후 재제출, 리더보드 확인). 완료율·소요 시간 기록 + SUS 설문 10문항 | 사용성 점수, 발견한 문제 → 수정 전후 비교 | 2시간 |
| 빈 상태 / 첫 사용 안내 | 제출이 0건일 때 "샘플 CSV로 먼저 연습해 보세요" 같은 안내 | 화면 | 1시간 |
| 마감 임박 알림 | 대시보드 배너 (D-1, 1시간 전), 남은 횟수 0일 때 경고 | 화면 | 1시간 |
| 관리자1 일괄 작업 | 다중 선택 재채점, 검토 의견 템플릿 관리, CSV 내보내기 | 화면 | 2시간 |

> **SUS (System Usability Scale)**: 사용성을 0~100점으로 수치화하는 표준 설문. 68점이 평균이고 80점 이상이면 우수로 본다. 숫자 하나로 "쓰기 편하다"는 주장을 객관화할 수 있다.

## 4. 시스템 설계 및 보안 (20점)

평가 문구: "**유지보수, 자원 사용량**, 보안 요구사항 등을 고려한 구현 및 설계인가?"

### 현재 계획의 강점
- 정답 프로세스와 코드 실행 프로세스의 분리, 샌드박스, 행안부 가이드 대응표, 감사 로그 해시 체인, 장애 대책 표

### 약점 (−5점 추정)
- **유지보수**: 설계 결정의 이유가 기획서에만 있고, 코드 저장소에 남는 형태(설계 결정 기록)가 아님
- **자원 사용량**: 평가 문구에 명시돼 있는데 **측정 계획이 없음**
- 자동화된 품질 관리(CI)가 없음

### 보강

| 보강 | 방법 | 결과물 | 소요 |
|---|---|---|---|
| **자원 사용량 측정** | `docker stats`로 유휴 상태와 부하 상태의 컨테이너별 CPU·메모리 기록. 샌드박스 1회 실행 시간과 메모리 측정 | "전체 시스템 유휴 시 ~N MB, 학생 50명 규모는 노트북 1대로 운영 가능" | 1시간 |
| **부하 테스트** | Locust로 "마감 5분 전 50명 동시 업로드" 시나리오 실행 | 응답 시간·실패율 그래프, 큐 처리 시간 | 2시간 |
| **CI 자동화** | GitHub Actions: 테스트 + `ruff` + `bandit` + `pip-audit`, README 배지 | 커밋할 때마다 자동 검증 | 1시간 |
| **설계 결정 기록 (ADR)** | 5건: 스택 선택, 프로세스 분리, 슬롯 예약 방식, 해시 선언 방식, pickle 처리 | `docs/adr/` | 1.5시간 |
| 테스트 커버리지 | 핵심 모듈(채점·순위·마감·권한) 90% 이상 | 배지 | 개발에 포함 |
| 설정 외부화 | 유예 시간·파일 크기·샌드박스 제한을 환경 변수로 관리 | `.env.example` 주석 | 개발에 포함 |

## 5. 문제 발견 및 창의적 개선 (20점)

평가 문구: "명시된 요구사항 **이외 스스로 문제를 발굴**하고 해결책 및 차별점을 제시할 수 있는가?"

### 현재 계획의 강점
- 오답 일치율, 해시 선언, 추론 재실행 검증, 규격 자동 추론, GIF 자동 생성

### 약점 (−5점 추정)
- 탐지 기능이 **실제로 잘 잡아내는지 증명하는 자료가 없음** (오탐하면 오히려 감점)
- 우리가 "스스로 발견한 문제"가 문서 곳곳에 흩어져 있어 **한눈에 보이지 않음**

### 보강

**① 부정 탐지 실험 (가장 효과가 큼)**
데모 데이터셋으로 네 종류의 제출을 만들고 탐지 결과를 표로 제시한다.

| 제출 유형 | 개수 | 만드는 방법 | 기대 |
|---|---:|---|---|
| 정직한 제출 | 20 | 서로 다른 모델 5종 × 하이퍼파라미터 4개 | 🟢 (오탐 0건이 목표) |
| 완전 복사 | 5 | 다른 사람 CSV 그대로 | 🔴 I-1 |
| 변형 복사 | 10 | 복사 후 5~20% 무작위 수정 | 🔴 I-2 오답 일치율 |
| 수기·조작 CSV | 10 | 정답 분포를 흉내 낸 무작위 값, 노트북은 정상 | 🔴/🟡 I-3, I-6 |

결과물: **탐지율·오탐률 표 + 오답 일치율 분포 그래프** (정직한 쌍과 복사한 쌍이 뚜렷하게 갈리는 그림 하나가 핵심). 발표 슬라이드 1장 분량.

**② "RFP가 놓친 문제 7가지" 정리** (발표 슬라이드 1장 + README 섹션)

| # | 우리가 발견한 문제 | 해결 |
|---|---|---|
| 1 | 업로드 시작만 해 두고 마감 후 파일을 바꿔치기할 수 있음 | 시작할 때 해시 선언 |
| 2 | 남은 횟수가 1회일 때 동시에 여러 번 제출하면 한도를 초과함 | 슬롯 예약 + 행 잠금 |
| 3 | 가중치 파일(pickle)은 불러오기만 해도 코드가 실행됨 | 샌드박스 안에서만 로드 |
| 4 | 부동소수 오차 때문에 같은 점수가 동점으로 처리되지 않음 | 표시 자릿수 기준으로 비교 |
| 5 | 성적을 엑셀로 내보낼 때 `=`로 시작하는 값이 수식으로 실행됨 (CSV 수식 주입) | 내보낼 때 이스케이프 |
| 6 | 정답 CSV를 그대로 배포 파일로 쓰면 정답이 유출될 수 있음 | 레이블을 자동 제거한 배포본 생성 |
| 7 | 관리자1의 가입 경로가 참여자와 같아 역할 구분이 모호함 | 역할별 참여 코드 |

**③ 차별점 명명** — 기능에 이름을 붙여 기억에 남게 한다. 예: "무결성 리포트", "업로드 서약(해시 선언)"
